## M1-01. Сервис и репозиторий подписок

✅ **Готово**

**Что вошло:**
- `subscriptionRepository` — каждый метод принимает `userId` и фильтрует по нему
- `subscriptionService` — создание, изменение, пауза, возобновление, мягкое удаление, восстановление
- Материализация прогнозов списаний на 12 месяцев, но не больше 12 событий
- Аудит на каждый переход состояния

**Готово, когда:**
- [x] Метода «получить подписку по id» без `userId` в проекте нет
- [x] Отмены в сервисе нет: `cancelled` ставит только `CancellationProvider`
- [x] Правка даты — единственный случай сдвига якоря
- [x] Отсутствие поля во входных данных не затирает его в базе
- [x] Тест изоляции на каждое действие

**Ключевое решение:** `updateOwned` использует `updateMany`, а не `update` — он принимает `userId` в условии, а `update` по одному id прошёл бы мимо проверки владения. Забыть проверку физически негде.

## M1-02. Server Actions

✅ **Готово**

**Что вошло:**
- `createSubscriptionAction`, `updateSubscriptionAction`, `pause`, `resume`, `delete`, `restore`
- Обёртка `runAction` — ошибки возвращаются значением, а не бросаются
- Zod-схемы с текстами ошибок по полям

**Готово, когда:**
- [x] Порядок соблюдён: валидация → аутентификация → владение → тариф → сервис → аудит
- [x] Лимит бесплатного тарифа проверяется на сервере
- [x] Форма получает ошибки по конкретным полям

**Ключевое решение:** действия вызываются из клиентских компонентов, где брошенное исключение React показал бы как безликую ошибку без текста. Внутри сервисов по-прежнему `AppError` — обёртка переводит его на границе.

## M1-03. Дашборд с итогами

✅ **Готово**

**Что вошло:**
- Итоги месяца и года в базовой валюте
- Триалы отдельным блоком выше остальных
- Ближайшие списания в окне 30 дней, блок «Позже», блок «На паузе»
- Честная пометка, если подписка не попала в итог из-за отсутствия курса

**Готово, когда:**
- [x] Итог сходится: 399 + 299 + 3990/12 = 1030,50 ₽
- [x] «В месяц × 12» совпадает с «в год»
- [x] Подписка на паузе не участвует в расходах
- [x] Ни одна подписка не пропадает из интерфейса

**Что вскрылось:** подписка со списанием дальше 30 дней не отображалась **нигде** — рендерились только триалы, ближайшие списания и пауза. Пользователь решил бы, что она потерялась. Добавлен блок «Позже».

## M1-06. Каталог сервисов РФ и СНГ

✅ **Готово**

**Что вошло:**
- 43 сервиса, 58 тарифов в `prisma/seed/services.ts`
- Домен `domain/catalog`: нормализация названий, транслитерация, расстояние Левенштейна
- Поиск с устойчивостью к опечаткам, раскладке и шумовым словам
- Комбобокс в форме с подсказками, клавиатурной навигацией и ARIA
- **Автоопределение категории** в два уровня

**Готово, когда:**
- [x] 43 сервиса с тарифами в базе
- [x] «kinopoisk», «кинопойск», «Кинопоиск HD» находят одну запись
- [x] Выбор сервиса подставляет сумму, валюту, период и категорию
- [x] Добавление из каталога — три действия: набрал, выбрал, сохранил
- [x] Ровно один тариф с `isDefault` — проверяется сидом, иначе он падает
- [x] 22 доменных теста, 8 сквозных

**Ключевые решения:**

*Поиск в памяти, а не в базе.* Каталог — десятки записей, меняется при выкатке сида. Расширение `pg_trgm` ради набора данных в пару килобайт было бы сложностью без выигрыша.

*Порог совпадения высокий (0.75).* Подставить не тот сервис хуже, чем не подставить ничего: пользователь не заметит подмену категории, но заметит неверную аналитику.

*Категория определяется в два уровня.* Сначала сервис ищется в каталоге — его категория точнее любой эвристики. Не нашли — работают ключевые слова: «VPN» → связь, «курсы» → обучение. Не угадали — поле остаётся пустым. Пустая категория честнее неверной.

*Угадывание не перебивает выбор пользователя* — подставляется только в пустое поле.

**Что осталось на потом:** цены требуют периодической сверки. Это отдельная задача сопровождения, а не разработки.

## M1-07. Онбординг сеткой сервисов

✅ **Готово**

**Что вошло:**
- Шаг 1: сетка из 12 популярных сервисов с ценами, отмечаешь плитками
- Шаг 2: для отмеченных — только дата, суммы подставлены из каталога
- Пропуск с отметкой `onboardedAt`
- Новый пользователь попадает в онбординг автоматически

**Готово, когда:**
- [x] Два экрана вместо ввода по одной подписке
- [x] Суммы подставлены — вводить их не нужно
- [x] Без выбора кнопка «Далее» неактивна и объясняет, чего ждёт
- [x] Отметка передаётся через `aria-pressed`, а не только цветом
- [x] Пропустивший не возвращается в онбординг при каждом заходе
- [x] Пройденный онбординг не открывается повторно
- [x] 9 сквозных сценариев

**Отступления от первоначального плана:**

*Валюта не занимает отдельный экран.* Она определяется по региону устройства и подставляется сама — целый шаг ради предзаполненного поля был бы данью формальности.

*Шаг выбора канала уведомлений пропущен.* Telegram ещё не подключён, in-app работает всегда — это был бы пустой экран. Вернётся на M2 вместе с каналами.

Итого два экрана вместо четырёх, что ближе к цели «90 секунд», чем исходный план.

**Ключевые решения:**

*Сортировка по категории, а не по «популярности».* Связанные сервисы оказываются рядом, и глаз пробегает сетку блоками. Данных о реальной популярности нет, а выдуманный порядок только притворялся бы осмысленным.

*Двенадцать плиток, а не все 43.* Полный каталог на первом экране топит в выборе; дюжины хватает, чтобы человек узнал половину.

*Названия подписок берутся из каталога на сервере.* Присланное клиентом могло быть подменено, а подписка должна называться так же, как сервис, на который ссылается.
