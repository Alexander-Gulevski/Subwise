## M2-01. Гиды отмены

⬜ **Не начата**

**Что войдёт:**
- Реализация `GuideCancellationProvider`
- Гиды для сервисов каталога: шаги, deep link, предупреждения, дата проверки
- Обратная связь «инструкция не сработала» с очередью на актуализацию

**Готово, когда:**
- [ ] Шаги описывают реальный интерфейс: «Выбери "Отключить продление"», а не «найди опцию отмены»
- [ ] `checkedAt` — дата фактической проверки, не сегодняшнее число «для порядка»
- [ ] Предупреждение про App Store и Google Play есть везде, где применимо
- [ ] `deepLink` ведёт в раздел управления подпиской, не на главную
- [ ] Гид старше 180 дней помечен как требующий проверки
- [ ] Ни одного выдуманного шага

**Самая частая и болезненная ошибка:** пользователь отменяет на сайте, а деньги списываются через Apple. Предупреждение об этом обязательно.

**Зависит от:** M1-06. **Зона ответственности:** агент `catalog-curator`.

## M2-02. Флоу отмены

⬜ **Не начата**

**Что войдёт:**
- Экран гида: предупреждения **до** шагов, дата проверки на виду
- Вопрос «Получилось отменить?» после возвращения пользователя
- Обработка четырёх исходов

**Готово, когда:**
- [ ] Ответ «Да» → `cancelled`, зафиксирована дата окончания доступа, запись в аудит
- [ ] Ответ «Нет» → статус **не изменился**, предложены пауза и напоминание
- [ ] «Вернусь позже» → создано напоминание
- [ ] «Инструкция не сработала» → `reportCount++`, статус не тронут
- [ ] Интерфейс **никогда** не пишет «отменено» до подтверждения
- [ ] Для сервиса без гида — общая инструкция, а не пустой экран

**Красная линия:** никакого оптимистичного обновления статуса отмены. Пользователь, уверенный в отмене при живой подписке, — главный репутационный риск категории.

## M2-03. Планировщик уведомлений

⬜ **Не начата**

Самая ответственная фоновая механика продукта.

**Что войдёт:**
- Очереди BullMQ, ежечасный проход
- `dedupeKey = hash(eventId, ruleId, channelId)`
- Двойная проверка: Redis и уникальный индекс в базе
- Тихие часы: откладывание, а не отмена

**Готово, когда:**
- [ ] Повторный запуск создаёт ровно одно уведомление на канал
- [ ] Очистка Redis не приводит к дублям — спасает `unique` в базе
- [ ] Падение одного канала не отменяет остальные
- [ ] Событие в тихих часах получает статус `deferred` и уходит после окна
- [ ] Повторный вызов cron-эндпоинта не имеет побочных эффектов

**Почему это критично:** дубли уведомлений — самый быстрый способ потерять пользователя в продукте, который живёт в напоминаниях.
