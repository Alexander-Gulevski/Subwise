# 07. Стратегия тестирования

> Статус: черновик на согласовании · Обновлён: 2026-07-27

## 1. Принцип

Мы не гонимся за процентом покрытия. Мы покрываем то, **где ошибка стоит дороже всего**:

1. **Деньги** — округления, конвертация валют, суммы в аналитике.
2. **Даты** — расчёт следующего списания. Классический источник тихих багов.
3. **Изоляция данных** — доступ к чужим подпискам.
4. **Идемпотентность** — дубли уведомлений.
5. **Состояния подписки** — переходы, особенно в `cancelled`.

Всё остальное покрывается по мере необходимости.

## 2. Пирамида

```
        ┌─────────────┐
        │  E2E (~10)  │  Playwright — только критические сценарии
        ├─────────────┤
        │ Интеграц.   │  Vitest + реальная PostgreSQL в Docker
        │   (~60)     │
        ├─────────────┤
        │   Юниты     │  Vitest, без базы и без сети
        │   (~200)    │
        └─────────────┘
```

| Уровень | Что проверяет | Скорость |
| --- | --- | --- |
| Юниты | Домен: деньги, даты, переходы состояний, правила уведомлений | < 5 с на весь набор |
| Интеграционные | Сервисы, репозитории, Server Actions — с настоящей БД | < 60 с |
| E2E | Сквозные сценарии в браузере | < 5 мин |

**Правило:** тест не должен требовать сети наружу. Внешние сервисы (ЦБ РФ, Telegram, почта) замоканы всегда.

## 3. Обязательные тесты

### 3.1. Деньги

| Что проверяем | Почему |
| --- | --- |
| Хранение и чтение в минорных единицах | Основа корректности всех расчётов |
| Конвертация валют не теряет копейки при сложении | Сумма частей должна равняться целому |
| Округление только на финальном шаге | Промежуточное округление накапливает ошибку |
| Отсутствие `float` в денежных полях | Проверяется тестом на схему, а не только ревью |
| Суммы в аналитике сходятся с суммой подписок | Расхождение подрывает доверие ко всему продукту |

### 3.2. Даты списаний

Отдельный набор с явными датами. Каждый случай — реальный источник ошибок:

| Случай | Ожидание |
| --- | --- |
| 31 января, `monthly` | 28 февраля (или 29 в високосный) |
| 28 февраля → следующий месяц, при якоре 31 | **31 марта**, не 28 марта |
| 29 февраля, `yearly`, невисокосный год | 28 февраля |
| Переход через год | Год увеличивается корректно |
| `custom` с `periodDays = 45` | +45 дней |
| Смена часового пояса пользователя | Дата события не сдвигается |

**Ключевой инвариант:** якорем расчёта служит исходный день месяца подписки, а не предыдущая вычисленная дата. Иначе подписка от 31 числа «сползёт» на 28 и останется там навсегда.

### 3.3. Изоляция данных

**Обязательный тест на каждый эндпоинт и Server Action.** Отсутствие — блокирующее замечание на ревью.

```
Дано:   пользователь A владеет подпиской S
Когда:  пользователь B запрашивает или изменяет S
Тогда:  ответ NOT_FOUND (не FORBIDDEN — иначе перебором узнаётся, что ресурс есть)
        и данные S не изменились
```

### 3.4. Идемпотентность уведомлений

| Сценарий | Ожидание |
| --- | --- |
| Планировщик запущен дважды для одного события | Ровно одно уведомление на канал |
| Redis очищен между запусками | Дубль всё равно не создаётся — спасает `unique` в БД |
| Один канал упал | Остальные доставлены, ошибка залогирована |
| Событие попадает в тихие часы | Статус `deferred`, отправка после окончания окна |
| Повторный вызов cron-эндпоинта | Побочных эффектов нет |

### 3.5. Переходы состояний подписки

| Переход | Ожидание |
| --- | --- |
| `active → cancelled` мимо `CancellationProvider` | Запрещено — сервис бросает ошибку |
| `confirmCancellation('succeeded')` | Статус `cancelled`, заполнены `cancelledAt` и `accessUntil`, запись в `AuditLog` |
| `confirmCancellation('failed')` | Статус **не изменился** |
| `trial` после `trialEndsAt` | Автопереход в `active`, создан `BillingEvent` |
| `paused` | Не участвует в расчёте расходов, `BillingEvent` не генерируются |
| `expired` | Финальное состояние, выход невозможен |

### 3.6. Тарифные ограничения

| Сценарий | Ожидание |
| --- | --- |
| `free` создаёт 11-ю подписку | `LIMIT_EXCEEDED` |
| `free` вызывает импорт напрямую через API | `PLAN_REQUIRED` — проверка на сервере, не только скрытием кнопки |
| `free` запрашивает аналитику за 12 месяцев | Данные обрезаны до 3 месяцев |

### 3.7. Импорт

| Сценарий | Ожидание |
| --- | --- |
| Импорт завершён | Созданы **только** `ImportCandidate`, ни одной `Subscription` |
| Кандидат отклонён | При повторном сканировании не предлагается снова |
| Кандидат совпадает с существующей подпиской | Помечен `duplicate` |
| Подключение отозвано | `credentialsEnc` очищен |

## 4. E2E-сценарии

Только то, что ломает продукт целиком:

| # | Сценарий |
| --- | --- |
| E1 | Регистрация через email OTP → онбординг → 3 подписки → дашборд показывает верную сумму |
| E2 | Добавление подписки из каталога занимает ≤ 3 действий |
| E3 | Полный флоу отмены: гид → «Да» → статус `cancelled`, показана дата окончания доступа |
| E4 | Флоу отмены с ответом «Нет» → статус **не изменился**, предложены альтернативы |
| E5 | Триал с окончанием через 2 дня виден на дашборде выше активных подписок |
| E6 | Смена базовой валюты пересчитывает итоги на дашборде |
| E7 | Пользователь B не видит подписки пользователя A |
| E8 | Приложение устанавливается как PWA и открывает дашборд офлайн |
| E9 | `free` упирается в лимит подписок и видит понятное объяснение |
| E10 | Экспорт данных отдаёт файл со всеми подписками |

## 5. Инструменты

| Задача | Инструмент |
| --- | --- |
| Юниты и интеграционные | Vitest |
| Компоненты | Testing Library — запросы по роли и тексту, не по CSS-классам |
| E2E | Playwright, проекты `chromium` и `mobile-chrome` |
| БД в тестах | PostgreSQL в Docker, отдельная база, чистится между наборами |
| Моки внешних API | MSW |
| Доступность | `axe-core` внутри E2E |

**Запрещено:** SQLite вместо PostgreSQL в тестах. Различия в типах и часовых поясах пропустят ровно те баги, которые мы ловим.

## 6. Что не тестируем

| Не тестируем | Почему |
| --- | --- |
| Внутренности Prisma и Next.js | Это работа их авторов |
| Точные CSS-значения | Хрупко и не ловит реальных дефектов |
| Геттеры и сеттеры без логики | Шум в наборе |
| Внешние API вживую | Медленно, нестабильно, зависит от сети |

## 7. Определение готовности

Задача считается выполненной, когда:

- [ ] Логика покрыта тестами уровня, соответствующего риску
- [ ] `tsc --noEmit` без ошибок, `strict: true`
- [ ] Линтер чист, включая правила границ слоёв
- [ ] Для эндпоинта есть тест на изоляцию данных
- [ ] Все четыре состояния экрана реализованы (загрузка, пусто, ошибка, норма)
- [ ] Проверена работа с клавиатуры и контраст
- [ ] Пользовательские строки в словарях, а не в коде
- [ ] Документация обновлена, если менялись контракты или модель данных

## 8. CI

```
push / pull request
  ├── tsc --noEmit
  ├── eslint (включая границы слоёв)
  ├── vitest run            (юниты + интеграционные, PostgreSQL в сервисе)
  ├── playwright test       (E2E)
  ├── npm audit
  └── сканер секретов
```

Красный CI блокирует merge. Флакающий тест либо чинится, либо удаляется — отключённый «на время» тест не существует.
