# 02. Архитектура

> Статус: черновик на согласовании · Обновлён: 2026-07-27

## 1. Технологический стек

| Слой | Технология | Почему |
| --- | --- | --- |
| Фреймворк | Next.js 15 (App Router) | Один проект на фронт и бэк. Telegram Mini App — это тоже веб, поэтому вторая платформа переиспользует тот же код |
| Язык | TypeScript, `strict: true` | Домен с деньгами и датами — типы обязательны |
| БД | PostgreSQL 16 | Транзакции, `numeric`, оконные функции для аналитики, зрелые бэкапы |
| ORM | Prisma | Типобезопасность от схемы до запроса, миграции в репозитории |
| Кэш и очереди | Redis | Rate limiting, кэш курсов валют, дедупликация уведомлений |
| Фоновые задачи | Планировщик на BullMQ | Напоминания требуют надёжного, идемпотентного расписания |
| UI | Tailwind CSS + Radix UI | Radix даёт доступность из коробки — это требование `NFR-02`, а не украшение |
| Валидация | Zod | Одна схема на клиент, сервер и типы. Граница доверия — всегда сервер |
| Тесты | Vitest, Testing Library, Playwright | См. [07-testing-strategy.md](07-testing-strategy.md) |
| Запуск | Docker Compose | Одинаково локально и на любом российском VPS |

Обоснование выбора — [ADR-0001](adr/ADR-0001-stack.md).

## 2. Принципы

1. **Домен не знает о фреймворке.** Бизнес-логика — чистые функции и классы без импортов из Next.js и Prisma. Их можно тестировать без базы и без браузера.
2. **Всё изменчивое — за интерфейсом.** Отмена, импорт, уведомления, оплата, авторизация имеют абстракции. Добавление реализации не меняет вызывающий код.
3. **Сервер — единственная граница доверия.** Клиентские проверки существуют для удобства. Права, лимиты тарифа и валидация проверяются на сервере всегда.
4. **Деньги — целые числа.** Минорные единицы, `bigint`/`Int`. `float` в денежных полях — ошибка ревью.
5. **Время — UTC в базе, локаль на отображении.** Все даты хранятся в UTC. Часовой пояс пользователя применяется только при рендере и при расчёте тихих часов.
6. **Идемпотентность фоновых задач.** Любая задача может выполниться дважды — результат должен быть тот же.

## 3. Структура проекта

```
src/
├── app/                      # Next.js App Router: маршруты и страницы
│   ├── (public)/             # Без авторизации: лендинг, каталог, гиды (SEO)
│   ├── (app)/                # Приложение: дашборд, подписки, аналитика, настройки
│   ├── api/                  # HTTP-эндпоинты: вебхуки, cron, Telegram
│   └── layout.tsx
│
├── domain/                   # ЯДРО. Без импортов из next, prisma, react
│   ├── subscription/         # Сущность, состояния, переходы, расчёт дат списаний
│   ├── billing-cycle/        # Вычисление следующей даты по периоду
│   ├── money/                # Минорные единицы, конвертация, форматирование
│   ├── analytics/            # Агрегации расходов и прогноз
│   └── notification/         # Правила напоминаний, тихие часы, дедупликация
│
├── ports/                    # Интерфейсы (контракты абстракций)
│   ├── CancellationProvider.ts
│   ├── ImportSource.ts
│   ├── NotificationChannel.ts
│   ├── BillingProvider.ts
│   ├── AuthProvider.ts
│   ├── OtpStore.ts           # хранилище кодов входа + отправка писем
│   └── ExchangeRateSource.ts
│
├── adapters/                 # Реализации портов
│   ├── cancellation/guide/
│   ├── import/csv/
│   ├── notification/{inapp,telegram,webpush,email}/
│   ├── billing/noop/
│   ├── auth/{telegram,email-otp}/
│   └── exchange-rate/cbr/
│
├── server/                   # Прикладной слой
│   ├── actions/              # Server Actions: точки входа мутаций
│   ├── services/             # Сценарии: связывают домен, порты и репозитории
│   ├── repositories/         # Доступ к данным через Prisma
│   ├── auth/                 # Сессии, guard-функции
│   └── jobs/                 # Фоновые задачи и планировщик
│
├── components/               # React-компоненты
│   ├── ui/                   # Примитивы дизайн-системы
│   └── features/             # Компоненты, привязанные к функциям
│
├── lib/                      # Утилиты без бизнес-логики
│   ├── env.ts                # валидация переменных окружения
│   ├── crypto.ts             # хеши, токены, AES-256-GCM
│   └── rate-limit.ts         # счётчики в Redis
│
└── locales/                  # Словари. Пользовательских строк в коде нет
```

> **Почему `crypto` и `rate-limit` лежат в `lib/`, а не в `server/`.**
> Ими пользуются адаптеры, а адаптерам импорт из `server/` запрещён.
> Это не обходной путь: обе утилиты не содержат бизнес-логики и не знают
> о доменных сущностях, поэтому `lib/` — их естественное место.
> Нарушение поймал линтер на первом же прогоне.

### Правило зависимостей

```
app / components  →  server  →  domain
                        ↓          ↑
                    adapters  →  ports
```

Стрелка — «может импортировать». Обратных стрелок не существует.

| Запрещено | Почему |
| --- | --- |
| `domain/` импортирует Prisma, Next.js или React | Домен должен тестироваться без инфраструктуры |
| `components/` импортирует Prisma напрямую | Доступ к данным — только через `server/` |
| `server/services/` импортирует конкретный адаптер | Только через порт, иначе абстракция бессмысленна |
| Бизнес-правило живёт в React-компоненте | Оно не будет переиспользовано в Telegram-боте |

Проверяется линтером (`eslint-plugin-boundaries`), а не только на ревью.

## 4. Ключевые абстракции

### CancellationProvider

Центральное архитектурное решение проекта. Позволяет начать с гидов и добавить автоматизацию, не переписывая продукт.

```ts
interface CancellationProvider {
  readonly kind: 'guide' | 'virtual-card' | 'automated';

  /** Может ли этот провайдер отменить подписку данного сервиса */
  supports(service: Service): boolean;

  /** Что показать пользователю: шаги гида или статус автоматической отмены */
  start(subscription: Subscription): Promise<CancellationFlow>;

  /**
   * Итог отмены. Для гида — ответ пользователя «получилось / не получилось».
   * Для автоматизации — результат выполнения.
   */
  confirm(flowId: string, outcome: CancellationOutcome): Promise<CancellationResult>;
}
```

**Инвариант:** подписка переходит в `cancelled` только через `confirm()`. Никакой другой код не меняет это состояние напрямую.

### ImportSource

```ts
interface ImportSource {
  readonly id: 'csv' | 'email' | 'bank';
  readonly requiredPlan: 'free' | 'pro';

  connect(userId: string, payload: unknown): Promise<ImportConnection>;
  /** Возвращает КАНДИДАТОВ. Никогда не создаёт подписки сам */
  scan(connection: ImportConnection): Promise<ImportCandidate[]>;
  disconnect(connection: ImportConnection): Promise<void>;
}
```

**Инвариант:** ни один источник импорта не создаёт `Subscription`. Только `ImportCandidate`, который подтверждает пользователь. Это защита от ложных срабатываний и потери доверия.

### NotificationChannel

```ts
interface NotificationChannel {
  readonly id: 'inapp' | 'telegram' | 'webpush' | 'email';

  isAvailableFor(user: User): Promise<boolean>;
  /** dedupeKey гарантирует, что повторный вызов не отправит второе сообщение */
  send(message: NotificationMessage, dedupeKey: string): Promise<DeliveryResult>;
}
```

**Инвариант:** отказ одного канала не влияет на остальные. Ошибка логируется, доставка по другим каналам продолжается.

## 5. Планировщик уведомлений

Самая ответственная фоновая механика продукта.

```
Каждый час:
  1. Найти BillingEvent, для которых наступило время напоминания
     (дата события − offset правила пользователя ≤ сейчас)
  2. Для каждого: сформировать dedupeKey = hash(eventId, ruleId, channelId)
  3. Если dedupeKey уже есть в Redis и в таблице доставок — пропустить
  4. Проверить тихие часы пользователя → при попадании отложить до конца окна
  5. Отправить по каждому включённому каналу независимо
  6. Записать результат доставки
```

**Почему так:**
- `dedupeKey` даёт идемпотентность (`NFR-05`) — планировщик можно перезапускать безопасно.
- Двойная проверка (Redis + БД) переживает очистку кэша.
- Независимая отправка по каналам — отказ Telegram не отменяет Email.
- Тихие часы откладывают, а не отменяют: пользователь не теряет напоминание.

## 6. Мультивалютность

```
Подписка хранит: amountMinor + currency  (исходная валюта, не меняется никогда)
Пользователь имеет: baseCurrency          (валюта отображения)
ExchangeRate хранит: currency + date + rateMinor  (из источника ЦБ РФ, раз в сутки)

Отображение = convert(amountMinor, currency → baseCurrency, курс на дату)
```

**Правила:**
- Пересчёт выполняется только на отображении и в агрегатах. Исходная сумма неприкосновенна.
- Курс недоступен → берётся последний известный, интерфейс это помечает (`NFR-05`).
- Округление — только на финальном шаге отображения. Промежуточные вычисления идут в минорных единицах.

## 7. Авторизация и сессии

```
AuthProvider (telegram | email-otp | …)
        ↓ подтверждает владение идентификатором
   AuthIdentity  ──many-to-one──→  User
        ↓
    Session (httpOnly cookie, 30 дней, скользящее продление)
```

- Один `User` может иметь несколько `AuthIdentity` — это позволяет войти через Telegram и через email в один аккаунт.
- Объединение аккаунтов — только после подтверждения владения обоими идентификаторами.
- Паролей нет в системе в принципе, поэтому нет и рисков их утечки.

## 8. Тарифы

Проверка доступа — на сервере, в одном месте:

```ts
// server/services/feature-access.ts
async function requireFeature(userId: string, feature: FeatureKey): Promise<void>
```

Вызывается в начале каждого Server Action и API-обработчика, требующего `pro`. Скрытие кнопки в интерфейсе — вежливость, а не защита (`FR-11`).

Платёж изолирован за `BillingProvider`. В MVP — `NoopBillingProvider`, который выдаёт `free` всем. Подключение YooKassa = новая реализация порта плюс вебхук, без изменений в остальном коде.

## 9. Развёртывание

```yaml
# docker-compose.yml — состав
app        # Next.js
worker     # BullMQ: планировщик и фоновые задачи
postgres   # БД
redis      # кэш, очереди, rate limiting
```

- Один `docker compose up` поднимает всё локально.
- Тот же compose переносится на российский VPS без изменений в коде.
- Секреты — только в переменных окружения. `.env` в `.gitignore`, в репозитории — `.env.example` с пустыми значениями.
- Миграции применяются отдельным шагом при деплое, не автоматически при старте приложения.

Подробности и обоснование — [ADR-0006](adr/ADR-0006-hosting.md).

## 10. Что архитектура сознательно откладывает

| Решение | Когда вернуться |
| --- | --- |
| Разделение на микросервисы | Не раньше, чем монолит перестанет справляться. Пока это только вред |
| Отдельный backend для мобильных приложений | При выходе за пределы PWA и Telegram |
| Event sourcing для истории подписок | Если понадобится полный аудит изменений. Пока хватает аудит-лога |
| Реплики БД для чтения | При появлении нагрузки, которой сейчас нет |

Принцип: не строить под нагрузку, которой нет. Но оставлять швы в местах, где рост наиболее вероятен — это и есть порты и адаптеры.
