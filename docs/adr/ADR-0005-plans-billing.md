# ADR-0005: Тарифы с первого дня, платёжный модуль — заглушка

## Статус
Принято · 2026-07-27

## Контекст

- Расширенные функции (импорт из почты, банка, CSV) заявлены как платные.
- Подключение YooKassa требует юрлица или ИП — это блокер, не зависящий от разработки (открытый вопрос Q2).
- Приём платежей в MVP не нужен: главная гипотеза — «люди готовы вести подписки в приложении», а не «люди готовы платить».
- Ретроспективное внедрение тарифов — болезненная операция: проверки доступа приходится добавлять в десятки уже написанных мест, и часть из них забывается.

## Решение

**Разделение тарифов существует с первого дня. Приём платежей — нет.**

1. Модель данных содержит `User.plan` (`free` | `pro`) и таблицу `FeatureFlag` с указанием требуемого тарифа.
2. Проверка доступа — **на сервере**, в одной функции:
   ```ts
   // server/services/feature-access.ts
   async function requireFeature(userId: string, feature: FeatureKey): Promise<void>
   ```
   Вызывается в начале каждого Server Action и API-обработчика, требующего `pro`.
3. Приём платежей изолирован за портом `BillingProvider`. В MVP — `NoopBillingProvider`, выдающий `free` всем.
4. Подключение YooKassa — это новая реализация порта плюс обработчик вебхука. Код вне модуля не меняется.

**Границы тарифов:**

| Функция | `free` | `pro` |
| --- | --- | --- |
| Подписки | до 10 | без ограничений |
| Ручной ввод | да | да |
| Каталог и гиды отмены | да | да |
| Все каналы уведомлений | да | да |
| Импорт (CSV, почта, банк) | нет | да |
| Аналитика | 3 месяца | полная |
| Экспорт данных | нет | да |

Уведомления намеренно бесплатны во всех каналах: они и есть механика удержания. Ограничивать их — вредить собственному ретеншену.

## Альтернативы

**Сделать всё бесплатным, тарифы добавить потом.**
Отклонено. Добавление проверок доступа задним числом означает обход всего написанного кода. Пропущенная проверка = дыра в монетизации, которую обнаружит первый же любопытный пользователь.

**Подключить YooKassa сразу.**
Отклонено. Требует юрлица, договора, интеграции чеков 54-ФЗ — недели работы до проверки главной гипотезы. Если гипотеза не подтвердится, эта работа выброшена целиком.

**Проверять тариф только на клиенте, скрывая кнопки.**
Отклонено как несерьёзное. Прямой вызов API обходит скрытую кнопку за минуту. Скрытие — вежливость к пользователю, защита — только на сервере.

**Хардкодить лимиты константами вместо таблицы `FeatureFlag`.**
Отклонено: пороги придётся подбирать на реальных данных (открытый вопрос Q5). Таблица позволяет менять их без релиза.

## Последствия

**Стало проще:**
- Подключение оплаты позже — локальное изменение в одном модуле.
- Границы тарифов видны и проверяемы с самого начала, их можно тестировать (`07-testing-strategy.md`, раздел 3.6).
- Пороги настраиваются без выкатки новой версии.

**Стало сложнее:**
- Каждая `pro`-функция требует явного вызова `requireFeature`. Забыть его легко — поэтому на каждую такую функцию обязателен тест «`free` получает `PLAN_REQUIRED`».
- Интерфейс должен осмысленно объяснять ограничение, а не просто прятать кнопку.

**Теперь запрещено:**
- Проверять тариф только скрытием элементов интерфейса.
- Обращаться к платёжному провайдеру мимо порта `BillingProvider`.
- Ограничивать каналы уведомлений тарифом.

## Когда пересмотреть

- Юрлицо оформлено и подтверждён спрос — подключается реальный `BillingProvider` (этап M4).
- Данные показали, что порог в 10 подписок отсекает не тех пользователей — меняется значением в `FeatureFlag`.
- Появилась потребность в третьем тарифе или в семейной подписке — потребуется расширить `Plan` за пределы двух значений.
