# Architecture Decision Records

Записи о принятых архитектурных решениях. Каждая фиксирует **контекст на момент решения**, рассмотренные альтернативы и последствия.

## Зачем это нужно

Через полгода никто не помнит, почему выбрали именно так. Без ADR решение либо переоткрывают заново, либо боятся трогать. ADR отвечает на вопрос «почему нельзя просто сделать иначе» — и, что важнее, показывает, при каких условиях сделать иначе будет уже можно.

## Формат

```markdown
# ADR-XXXX: Название

## Статус
Предложено | Принято | Заменено на ADR-YYYY | Устарело

## Контекст
Что мы знали на момент решения. Какие ограничения действовали.

## Решение
Что решили. Формулировка в настоящем времени: «Мы используем…»

## Альтернативы
Что ещё рассматривали и почему отклонили. Без этого раздела ADR бесполезен.

## Последствия
Что стало проще. Что стало сложнее. Что теперь запрещено.

## Когда пересмотреть
Конкретные условия, при которых решение перестаёт быть верным.
```

## Правила

- ADR **не редактируется** после принятия. Изменилось решение — пишется новый ADR со статусом «Заменяет ADR-XXXX», старый получает «Заменено на ADR-YYYY».
- ADR пишется **до** реализации, а не как отчёт постфактум.
- Раздел «Альтернативы» обязателен. Решение без отвергнутых вариантов — это не решение, а привычка.
