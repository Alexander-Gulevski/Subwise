# ADR-0004: Деньги в минорных единицах, пересчёт валют на отображении

## Статус
Принято · 2026-07-27

## Контекст

- Многие популярные в РФ сервисы списывают в валюте: Spotify, Steam, зарубежные облака и VPN.
- Пользователь хочет видеть общую сумму в одной, понятной ему валюте.
- Курсы меняются ежедневно, а исторические расходы должны оставаться воспроизводимыми.
- Некорректные суммы — прямой удар по доверию: если итог на дашборде не сходится, продукт бесполезен.
- Классическая ошибка: `0.1 + 0.2 !== 0.3` в двоичной плавающей арифметике.

## Решение

**Хранение:**
- Все денежные величины — целое число в минорных единицах: `amountMinor: Int`. 399,00 ₽ хранится как `39900`.
- Валюта хранится рядом с суммой: `currency: String` (ISO 4217).
- **Исходная сумма и валюта не изменяются никогда.** Подписка в долларах остаётся подпиской в долларах.

**Пересчёт:**
- Пользователь задаёт `baseCurrency` в настройках (по умолчанию RUB).
- Курсы загружаются из источника ЦБ РФ раз в сутки в таблицу `ExchangeRate` с привязкой к дате.
- Конвертация выполняется **только на отображении и в агрегатах**, никогда при записи.
- Округление — только на финальном шаге вывода. Все промежуточные вычисления идут в минорных единицах.

**Деградация:**
- Курс недоступен → берётся последний известный, ответ помечается `isStale: true`, интерфейс показывает дату курса.
- Отсутствие курса не блокирует работу приложения (`NFR-05`).

**Формат в API:**
```json
{
  "amount":    { "minor": 1099, "currency": "USD" },
  "converted": { "minor": 98000, "currency": "RUB", "rateDate": "2026-07-27", "isStale": false }
}
```

## Альтернативы

**Хранить деньги в `Float` или `Double`.**
Отклонено безоговорочно. Двоичная плавающая арифметика не представляет десятичные дроби точно. При суммировании десятков подписок ошибка становится видимой пользователю, и никакое «округлим при выводе» её не лечит.

**Хранить в `Decimal` (`numeric` в PostgreSQL).**
Работает корректно, но Prisma отдаёт `Decimal` как объект, требующий отдельной библиотеки на каждой арифметической операции по всему коду. Целые минорные единицы дают ту же точность при более простой арифметике. Отклонено в пользу простоты.

**Конвертировать при сохранении, хранить только в базовой валюте.**
Отклонено. Исходная сумма теряется безвозвратно: при смене базовой валюты историю уже не пересчитать корректно, а пользователь перестаёт узнавать свои же суммы в выписке.

**Брать курс в реальном времени при каждом запросе.**
Отклонено: внешняя зависимость на горячем пути рендера, непредсказуемая задержка и разные итоги при двух подряд открытиях дашборда.

**Хранить курс на момент каждого списания.**
Частично принято: `BillingEvent` фиксирует `amountMinor` и `currency` на момент события — цена подписки могла измениться. Курс же берётся на дату из справочника, чтобы история оставалась воспроизводимой.

## Последствия

**Стало проще:**
- Арифметика — целочисленная, без потерь точности.
- Исходные данные пользователя неприкосновенны, смена базовой валюты безопасна.
- История расходов воспроизводима: пересчёт по курсу на дату даёт тот же результат всегда.

**Стало сложнее:**
- Каждое отображение суммы проходит через слой форматирования — нельзя просто вывести число.
- Нужен фоновый процесс загрузки курсов и обработка его сбоев.
- Разработчику нужно помнить про минорные единицы. Смягчается типом-обёрткой в `domain/money/` и тестами.

**Теперь запрещено:**
- Тип `Float` или `Decimal` в денежных полях схемы.
- Конвертация валют при записи в БД.
- Округление в промежуточных вычислениях.
- Вывод суммы напрямую, минуя `Intl.NumberFormat`.

## Когда пересмотреть

- Понадобилась точность выше двух знаков (например, курсы с четырьмя знаками в отдельном расчёте) — тогда для конкретного поля вводится отдельный масштаб.
- Появились суммы, выходящие за пределы `Int` — переход на `BigInt`.
- Источник ЦБ РФ перестал покрывать нужные валюты — потребуется второй источник и правило приоритета.
