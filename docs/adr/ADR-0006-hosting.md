# ADR-0006: Docker Compose как единица развёртывания

## Статус
Принято · 2026-07-27

## Контекст

- Аудитория — граждане РФ. 152-ФЗ требует хранить их персональные данные на серверах в России.
- Конкретный хостинг на старте не выбран: Yandex Cloud, Selectel, Timeweb — решение отложено сознательно.
- Разработка ведётся локально на Windows, продакшн будет на Linux.
- Нужны четыре компонента: приложение, воркер фоновых задач, PostgreSQL, Redis.
- Vercel и подобные платформы дают быстрый деплой, но размещают данные за рубежом.

Ключевое требование: **выбор площадки не должен требовать изменений в коде.** Иначе решение о хостинге превращается в блокер разработки.

## Решение

Единица развёртывания — `docker-compose.yml` с четырьмя сервисами:

```yaml
app        # Next.js
worker     # BullMQ: планировщик уведомлений и фоновые задачи
postgres   # PostgreSQL 16
redis      # кэш, очереди, rate limiting
```

**Правила:**
- `docker compose up` поднимает полное окружение локально — одинаково у любого разработчика и на любой ОС.
- Тот же compose переносится на российский VPS без изменений в коде приложения.
- Вся конфигурация — через переменные окружения. `.env` в `.gitignore`, в репозитории только `.env.example` с пустыми значениями.
- Миграции БД применяются **отдельным шагом деплоя**, не автоматически при старте контейнера.
- Воркер — отдельный контейнер, а не поток внутри приложения.

## Альтернативы

**Vercel + Neon (или другой зарубежный serverless).**
Самый быстрый деплой. Отклонено по двум причинам: персональные данные граждан РФ уезжают за рубеж, что конфликтует с 152-ФЗ; плюс риск недоступности сервиса для российских пользователей. Скорость деплоя не стоит юридического риска в продукте с финансовыми данными.

**Сразу выбрать Yandex Cloud с управляемыми сервисами.**
Отклонено на старте: привязывает к площадке до того, как понятны реальные потребности и стоимость. Переезд с управляемого PostgreSQL на другой требует работы. Compose оставляет выбор открытым — управляемая БД подключается заменой переменной окружения.

**Развернуть на VPS без контейнеров, напрямую.**
Отклонено: расхождение окружений «работает у меня» — источник трудноуловимых проблем. Windows локально и Linux в проде делают это почти неизбежным.

**Kubernetes.**
Отклонено. Нагрузки, оправдывающей его, не существует и в ближайшее время не появится. Операционная сложность сразу, польза — гипотетически.

**Приложение и воркер одним процессом.**
Отклонено: тяжёлая фоновая задача заблокирует обработку запросов пользователей, а масштабировать их придётся независимо.

## Последствия

**Стало проще:**
- Локальное окружение поднимается одной командой, без ручной установки PostgreSQL и Redis.
- Решение о хостинге отложено без блокировки разработки.
- Смена площадки не затрагивает код.
- Локальная среда идентична продакшену.

**Стало сложнее:**
- Бэкапы, мониторинг, обновления TLS-сертификатов настраиваются вручную — управляемая платформа делала бы это за нас.
- Нужен Docker на машине разработчика.
- Первый деплой требует больше ручной работы, чем `git push` на Vercel.

**Теперь запрещено:**
- Использовать API конкретной платформы (Vercel KV, Vercel Blob и аналоги) — это привязка, ломающая переносимость.
- Хранить секреты где-либо, кроме переменных окружения.
- Применять миграции автоматически при старте контейнера — это делает откат опасным.

## Когда пересмотреть

- Ручное обслуживание инфраструктуры начало отнимать заметное время — переход на управляемые сервисы Yandex Cloud, при сохранении Compose для локальной разработки.
- Появилась нагрузка, требующая горизонтального масштабирования, — тогда есть смысл вернуться к оркестрации.
- Юридическая ситуация изменилась настолько, что зарубежный хостинг стал допустим (маловероятно).
