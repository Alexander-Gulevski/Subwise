# Агенты проекта Subwise

Каждый файл в этой папке описывает одного агента: его зону ответственности, **разрешённые инструменты** и правила работы.

## Зачем разграничивать права

Поле `tools` в заголовке файла — это не документация, а реальное ограничение. Агент физически не может вызвать инструмент, которого нет в списке.

Практический смысл:

- **`security-auditor` и `code-reviewer` не имеют `Write` и `Edit`.** Они находят проблемы и докладывают, но не правят код сами. Ревьюер, который молча чинит найденное, лишает смысла само ревью — изменения проходят мимо внимания.
- **`architect` не имеет `Bash`.** Он проектирует и пишет документы, а не запускает миграции и сборки.
- **`catalog-curator` имеет `WebSearch`, но не `Bash`.** Он собирает данные о сервисах, ему незачем трогать инфраструктуру.

## Как запускать

```
Используй агента backend-dev, чтобы реализовать расчёт дат списаний из docs/03-data-model.md
```

Агент стартует с **чистым контекстом** — он не видит эту переписку. В запросе нужно указать, что делать и на какие документы опираться. Правила из его файла подгружаются автоматически.

## Общие правила для всех агентов

Действуют независимо от роли и имеют приоритет над задачей:

1. **Документация — источник истины.** Расхождение кода и документа — дефект. Если требование мешает, нужно сказать об этом, а не решить молча иначе.
2. **Не выходить за свою зону.** Нашёл проблему в чужой области — сообщи, не чини сам.
3. **Красные линии из [06-security-privacy.md](../../docs/06-security-privacy.md) не обходятся** ради удобства функции. Никогда.
4. **Термины — из [glossary.md](../../docs/glossary.md) дословно.** Нового понятия нет в глоссарии — сначала добавь его туда.
5. **Не начинать реализацию, если требование неоднозначно.** Уточнение дешевле переделки.
6. **Отчитываться честно.** Тест падает — сказать прямо и показать вывод. Шаг пропущен — сказать, что пропущен.
